# 测试用例编写规范

后续新增和优化用例默认按本规范编写，适用于正式需求及工作流、界面等专项。目标是让执行人员根据条目直接准备、操作和判定，减少重复说明，同时保留完整验收范围。具体范围以用户已确认要求和对应需求为准。

## 固定格式

沿用九列：`ID｜优先级｜前置条件｜操作步骤｜预期结果｜来源｜自动化｜脚本｜设计备注`。旧表末列名为“锚点提示”的可按原映射维护，不增加执行结果列。正式需求从[模板](_template.md)填写。

| 内容 | 写法 |
|---|---|
| 标题 | 简短说明功能与场景，放在操作步骤首行；保留已有定位锚点。不把整段提示词当标题，也不为每条反复添加版本名称。 |
| 前置条件 | 只写本例必需的环境/账号、素材和工程状态，以及可独立核准的基线。明确素材名或角色、是否已分析、目标文字/时间、轨道及关联关系。 |
| 操作步骤 | 按“1.、2.、3.”编号，表格内以`<br>`分行。写清入口、动作、完整可复制提示词、参数和必要等待；准备操作与被测动作分开。 |
| 预期结果 | 写明核对对象、具体变化、必须保留的内容和异常反馈，让执行人员能明确判定。必要时检查播放、听审、下载、保存及重开结果。 |
| 来源与映射 | 保留需求条款或用户确认依据、优先级、自动化实现状态及实际脚本路径；推断风险与正式要求分别注明。 |
| 设计备注 | 仅写必要的设计边界或分类。修订原因与版本追溯在配套修订记录集中维护，不逐条重复装饰性标签。 |

## 前置与步骤

1. 仅准备本例需要的对象，不默认要求整套视频、配音、BGM、水印及其他无关条件。共用素材规格放配套数据文档，本条仍要说清使用哪份素材及什么状态。
2. A/B工程、C1字幕等角色在本条直接说明含义；使用真实工程名、原文、时间登记目标。不要只写未定义的P、B0、E或“按上一条准备”。无关的详细工程名称无需写入提示词。
3. 基线通过原素材、核准清单或既有可靠证据独立确认，不能把本次产品输出反过来作为预期。声音、画面不存在等金标需满足对应听审或观看要求。
4. 提示词应简洁且完整，保留目标、动作、数值及必要约束；替换位置写清楚，固定参数不得随意替换。优化既有条目时保留原触发指令；确需更换指令，应记为设计修订，原指令及历史结果可追溯。
5. 简单场景通常3～4步，复杂场景按实际需要展开。多轮指令逐轮写全，明确先后、等待、刷新或切换时点；不以“发送P1～P4”代替正文。参数组、正常/异常对照、恢复及账号/浏览器分组均须保留。
6. 测试自然语言编辑的目标动作通过对话执行；不能以手工按钮或直接API代替。原本明确安排的手工操作、真实接口专项及技术精度要求仍按原范围保留。
7. 真实澄清按条目目标回答并记录；专门验证澄清或无补槽的场景注明判定条件。任务受理不明时先回读，不重发已受理任务。
8. 复杂前置可拆为单项准备、保存回读和基线冻结，再执行被测动作。缺条件只阻塞依赖分支，不把整组关联、原子提交或一次撤销改为独立修改来降低标准。

## 预期与范围保护

- 对照实际工程、文件和画面/声音判定；助手回复“完成”不能单独证明成功。写清改了什么、哪些内容应保持，以及保存重开等原要求是否成立。
- 正式需求明确要求的业务能力缺失时，保留失败检查点；不能为精简改成“不适用”或删除。未明确支持的能力和未公布的限值不自行假定，先核对依据。
- 保留原验收范围、编号、优先级、需求来源、完整参数组和轮次，以及自动化/脚本映射。优化文案不改变原执行结论，不把人工或有头浏览器执行标成固定脚本已实现。
- 需要真实U2、特殊关联、故障控制或独立基线的场景，必须保留这些前置；普通报错、同账号或合成成片不能替代。
- 用户明确变更范围时，独立记录新旧范围、版本和重评依据；旧实测、未覆盖事实和证据保留。修订本身不代表新测试通过或产品修复。

## 设计与执行分开维护

用例正文只维护设计。实际通过/失败/阻塞、执行日期、截图、缺陷链接、云效状态、批次统计和任务断点写入独立执行报告、状态表/JSON及进度文档。清理既有正文时，原执行记录完整移入历史归档并保留追溯关系。

每条实际执行结束，及时更新独立状态、报告及进度，注明使用的设计版本、实际证据和脚本实现/运行情况。仅整理文档时，原状态和证据保持，不补算执行。

[统一入口](README.md)只保留分类、正文、脚本、命令及稳定说明的导航。正式需求在`docs/cases/requirements/`原目录维护；工作流专项保留在`docs/design-cases/`对应分类，不重复复制或擅自重编号。

需要同步云效时，按用户授权更新原用例并回读核验；编辑定义与更新执行状态分别处理，保留既有编号及执行状态，避免重复导入。写作规范本身不构成云效同步授权。

## 交付前检查

- 标题清楚；前置足够且无无关堆叠；步骤编号、完整指令和参数可直接执行；预期可核对。
- 原编号、九列、需求来源和链接完整；所有参数组、分支、轮次及验收点均保留。
- 原执行状态、自动化状态、脚本映射及历史证据未因文案整理被改判。
- 正式需求用例变更后执行`npm run cases:check`；该检查主要验证结构，仍需对照原文核对范围、提示词与参数。
